# 트리거 재현율 테스트 — 실제 저장소 2건 (board)

`github.com/hojunnnnn/board` — Spring Boot + JPA + Spring Security로 만든 게시판 프로젝트(회원가입/로그인/OAuth 포함). RunningGu와 비교하기 위해 트리거 1(생년월일→미성년자 동의)만 좁혀서 재검증. 얕은 클론 후 grep + 핵심 파일 2개만 확인.

## 결과

`User.java`(엔티티), `UserDto.java`(회원가입 요청 DTO)를 직접 열어봤다. 필드는 `username, nickname, password, email, role` 뿐이고 **나이·생년월일 관련 필드나 검증 로직이 전혀 없다.** `@Pattern` 검증(아이디 형식, 비밀번호 강도, 이메일 형식)은 꼼꼼히 되어 있는데 나이 확인만 통째로 빠져 있다.

grep으로 `birthDate|birthday|생년월일|dateOfBirth|ageOver|만.?14세|나이`를 전체 저장소에 돌려도 **매치 0건**.

## RunningGu와의 비교

| | RunningGu | board |
|---|---|---|
| 나이 확인 방식 | 자기신고형 boolean(`ageOver14`) | **없음** |
| 트리거 1 코드 패턴으로 탐지 가능? | 가능(boolean 필드명으로 매치) | **불가능** (검색해서 찾을 대상 자체가 없음) |
| 실제 위험도 | 중간 (자기신고 미검증 문제는 남음) | **높음** (미성년자 가입을 막을 장치가 전무) |

## 결론 — 트리거 1의 설계를 바꿔야 함

"코드에 이 패턴이 있으면 걸린다"는 존재-탐지 방식으로는 board 같은 **부재형 사례**를 잡을 수 없다. 이건 트리거 목록 전체의 감지 방식에 대한 문제 제기이기도 하다: 회원가입 폼(이메일/비밀번호 필드가 있는 User 엔티티나 SignUp DTO)이 감지되면, 그 안에 나이 확인 관련 필드가 **있는지 없는지**를 같이 확인해야 한다 — "무엇이 보이면 경고"가 아니라 "무엇이 보이는데 특정 게 안 보이면 경고"하는 규칙이 필요하다.

`rules/triggers.md` 1번에 이 세 번째 변형(부재형)을 반영해뒀다. SKILL.md의 절차(`workflows/trigger-to-verification.md`)에도 "회원가입 폼 발견 시 나이 확인 로직 존재 여부를 먼저 확인"하는 단계를 넣는 게 좋아 보인다 — 다음 개선 과제로 남긴다.
