# 엔드투엔드 드라이런 — board 저장소

목적: `rules/triggers.md`(감지) → `rules/legal-reasoning.md`(원칙) → `workflows/trigger-to-verification.md`(law.go.kr 검증) → `rules/uncertainty.md`(라벨) → `templates/legal-review-report.md`(출력)까지 전 과정을 실제로 한 번 이어서 실행해본 기록. 지금까지는 각 부품만 따로 확인했지, 전체가 실제로 이어지는 걸 본 적이 없었다.

**대상 코드**: `github.com/hojunnnnn/board`의 `User.java`(엔티티), `UserDto.java`(회원가입 요청 DTO) — [examples/repro-test-board.md](repro-test-board.md)에서 이미 확인한 실제 저장소.

---

## 1단계 — 감지 (rules/triggers.md 대조)

회원가입 폼(`UserDto.Request`: username, password, nickname, email)이 보인다. 대조 결과 2개 트리거 매치:

- **1번**: 나이/생년월일 관련 필드·검증이 전혀 없음 → 부재형 매치(트리거 1의 세 번째 변형)
- **35번**: 개인정보(이메일 등) 수집 폼은 있는데 저장소 어디에도 개인정보처리방침 페이지·문구가 없음(grep 확인) → 부재형 매치

다른 트리거는 해당 없음(결제·크롤링·AI API 등 코드 없음) — 억지로 코멘트 안 붙임.

## 2단계 — 원칙 적용 (rules/legal-reasoning.md)

- 트리거 ≠ 결론 원칙에 따라 "위반이다"라고 바로 단정하지 않음 — "확인이 필요한 지점"으로만 제시
- 부재형 트리거이므로 "코드에 이게 있다"가 아니라 "있어야 할 게 없다"는 걸 명확히 표현

## 3단계 — 검증 호출 (workflows/trigger-to-verification.md, law.go.kr 직접 조회)

두 트리거 모두 이번 세션에서 실제로 law.go.kr 원문을 열어 확인함(Browser 도구 사용):

- 1번 → 개인정보보호법 제22조의2(아동의 개인정보 보호), 제64조의2(과징금)
- 35번 → 개인정보보호법 제30조(개인정보 처리방침의 수립 및 공개)

## 4단계 — 라벨링 (rules/uncertainty.md)

둘 다 원문을 직접 대조했고 최신 개정 여부(1번은 2023-03-14 신설 조문, 시행 중)도 확인했으므로 `[VERIFIED]`.

## 5단계 — 출력 (templates/legal-review-report.md 형식)

아래는 LawLint가 이 코드를 봤을 때 실제로 출력할 내용이다.

## 드라이런에서 드러난 문제

1. **1번 트리거의 조문 번호가 이번에 처음 채워졌다.** Day 2부터 지금까지 "가장 중요한 사례"라고 스스로 불러온 1번이 정작 실제 조문 인용 없이 방치돼 있었다 — 드라이런을 실제로 끝까지 돌려보지 않았다면 이 구멍을 몰랐을 것이다. 부품 단위 테스트(재현율 테스트, 할루시네이션 테스트)로는 안 잡히고, 전체를 이어서 출력까지 만들어봐야 잡히는 종류의 문제였다.
2. **출력 포맷 자체는 잘 작동한다** — `templates/legal-review-report.md`가 요구하는 필드(코드 위치, 관련 가능성, 상태, 확인 경로, 확인이 필요한 것, 참고 링크)가 실제로 다 채워졌다.
3. **부재형 트리거 2개가 동시에 걸리는 실제 사례**를 처음 봤다 — "코드 위치"란이 "저장소 전체"처럼 애매해지는 문제를 실제로 겪었다(35번은 특정 파일이 아니라 "없다"는 사실 자체가 위치이므로). 드라이런 도중 `templates/legal-review-report.md`를 바로 수정 — "코드 위치"를 "확인 대상"으로 바꾸고 부재형 전용 표현 예시를 추가했다.
