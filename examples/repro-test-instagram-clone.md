# 트리거 재현율 테스트 — 실제 저장소 5건 (Instagram-Clone-Project)

`github.com/jyo925/Instagram-Clone-Project` — Spring Boot + JPA + JSP로 만든 인스타그램 클론(이미지 업로드, 팔로우, 좋아요, 댓글).

## 결과

| 트리거 | 결과 |
|---|---|
| 1 (나이 확인) | **또 부재형 — 5전 5패.** 나이 관련 필드·검증 0건. 5개의 서로 다른 도메인(러닝·게시판·이커머스·AI챗봇·SNS) 프로젝트 전부에서 나이 확인이 없거나 불완전했다 |
| 16 (UGC 저작권 신고 체계) / 37 (불법촬영물 유통방지 책임자) | **부재형으로 둘 다 매치.** `ImageController`/`ImageUploadDto`로 이미지 업로드는 있는데, `report`/`신고`/`block`/`차단` 관련 코드가 전혀 없다 — 신고·삭제 요청 처리 기능 자체가 없음. 1번과 마찬가지로 "이미지 업로드는 있는데 신고 기능이 없다"는 부재형 패턴으로 처리해야 함 |
| **12 (구독 다크패턴) — 오탐 방지 사례 발견** | `SubscribeDto`, `Subscribe` 엔티티가 있어서 매치될 뻔했지만, 실제로 열어보니 **"구독"은 결제가 아니라 인스타그램의 "팔로우" 기능**이었다(`fromUser`/`toUser`, 가격·결제주기 필드 없음). 한국어 "구독"이 (a) SNS 팔로우, (b) 유료 정기결제 두 가지 뜻으로 다 쓰이는데, 코드에 결제·가격 필드가 있는지 확인 안 하면 팔로우 기능에 다크패턴 규제를 잘못 적용하게 됨 |

## 5개 저장소 누적 요약

| 트리거 | 상태 |
|---|---|
| 1 (나이 확인) | **5/5 미흡** — 부재형 감지가 LawLint에서 가장 자주 쓰일 규칙임을 재확인 |
| 16, 37 (UGC 신고 체계) | 부재형으로 매치 — 1번과 같은 패턴군으로 묶어서 처리 가능 |
| 12 (구독 다크패턴) | 단어("구독")만 보고 걸면 오탐 — 결제/가격 필드 존재 여부까지 확인해야 함 |
| 8 (AI 학습 재사용) | "AI 챗봇 존재" 자체가 아니라 "사용자 대화를 학습에 쓰는지"로 좁혀야 함 (rag-chatbot 사례) |
| 29~34 (세무) | 모의/테스트 결제(Mock PG)와 실제 결제를 구분해야 함 (ecommerce 사례) |
| 43 (리뷰 조작) | 정상 리뷰 코드엔 반응 안 함 — 참 부정 확인됨 (ecommerce 사례) |
| 41 (보호조치) | 접근통제 테스트가 있으면 긍정 신호로 인정 (rag-chatbot 사례) |

## 종합 결론

5개 저장소, 5개 도메인을 테스트한 결과 트리거는 크게 세 유형으로 나뉜다는 게 명확해졌다:
1. **부재형**(1, 16, 35, 36, 37번 등) — "있어야 할 게 없으면" 걸림. 실무에서 가장 흔함
2. **존재형 — 단순 매치**(2, 11번 등) — 코드에 패턴이 있으면 걸림. 비교적 명확
3. **존재형 — 문맥 확인 필요**(8, 12, 29~34번 등) — 패턴은 있어도 "진짜 그 문제가 맞는지"(학습재사용인지 RAG인지, 결제인지 팔로우인지, 실결제인지 모의결제인지) 한 번 더 확인해야 오탐을 피할 수 있음
